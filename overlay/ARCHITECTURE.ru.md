# Адаптер шлюза МАКС — архитектура и алгоритмы

Этот документ описывает внутреннее устройство адаптера мессенджера МАКС и то, как оно реализовано в файлах исходного кода.

## 1. Обзор и поток данных

Адаптер превращает поток обновлений MAX Bot API в ходы сессий Coddy и отправляет ответы обратно в чат.

```
GET /updates (длинный опрос)
        ↓
client.go  разбирает страницу по одному Update
        ↓
poll.go    передаёт каждый Update в Bot.Handle
        ↓
dispatch.go  маршрутизирует коллбэки, дедуплицирует сообщения,
             проверяет ACL, строит ключ сессии, ставит ход в очередь
        ↓
воркер сессии (один на ключ сессии) выполняет ход
        ↓
runner.HandleSessionPromptWithSender(ctx, params, sender, opts)
        ↓
sender.go  (acp.UpdateSender) публикует/правит живое сообщение,
           разбивает длинные ответы, рисует клавиатуры
        ↓
чат МАКС
```

Точка входа: `external/gateway/serve_max.go` собирает `Bot` и запускает `gateway.Hub`. Hub перезапускает бота при ошибке; `Bot.Start` работает до отмены контекста.

## 2. Транспорт — `external/gateway/max/client.go`

`Client` — рукописный HTTP-клиент для MAX Bot API.

### Авторизация и формат запроса
- Токен передаётся в заголовке `Authorization` в сыром виде, без префикса `Bearer` (`NewClient`, `once`).
- Базовый URL по умолчанию — `https://platform-api2.max.ru`; переопределяется через `CODDY_MAX_API_BASE` (`apiBaseURL` в `bot.go`, `WithBaseURL`).

### HTTP-клиент и TLS
- `bot.go` собирает HTTP-клиент через `proxyutil.BuildHTTPClient(cfg.Proxy)` и, если задан `cfg.CAFile`, дополняет системное хранилище сертификатов PEM-пакетом (`withRootCA`). Транспорт клонируется, чтобы настройки шлюза не меняли `http.DefaultTransport`.
- Таймаут запроса по умолчанию — `poll timeout + 15 с`, чтобы удерживаемый длинный опрос не обрывался раньше времени.

### Endpoint'ы
- `Me(ctx) (User, error)` — `GET /me`. Используется при старте для проверки токена и чтения `selfID`/`name`.
- `fetchUpdates(ctx) ([]Update, int64, error)` и `Updates(ctx) ([]Update, error)` — `GET /updates`. Низкоуровневый вызов возвращает разобранную страницу и новый маркер, не сдвигая курсор; обёртка сдвигает курсор.
- `Send(ctx, Outgoing) (string, error)` — `POST /messages`. Возвращает идентификатор сообщения (`mid`), присвоенный МАКСом.
- `EditMessage(ctx, messageID, text, buttons)` — `PUT /messages`. `nil`-клавиатура оставляет вложения без изменений; пустой ненулевой срез удаляет их.
- `EditText(ctx, messageID, text)` — `PUT /messages` с `buttons == nil`.
- `AnswerCallback(ctx, callbackID, notification)` — `POST /answers`.

### Повторные попытки и ограничение скорости
- `do` зацикливается только на 429, читая `Retry-After` (ограниченный `maxRetryAfter` = 60 с) и нарастая экспоненциально, если заголовок отсутствует.
- Для записей повторяется только 429; остальные HTTP-ошибки и сетевые сбои возвращаются сразу, потому что сервер мог уже обработать запрос.
- `IsTransient(err)` отмечает сетевые/серверные/рейтлимитные ошибки; `IsStatus(err, status)` проверяет конкретный HTTP-статус.

### Ограничитель скорости (pacer)
- `pacer` разносит каждый POST/PUT/DELETE на `writeGap` = 500 мс (~2 записи/с), общий для всех отправителей одного бота, потому что лимит привязан к токену. GET не регулируется.

### Ошибки
- `APIError` несёт HTTP-статус, `code`, `message` и `Retry-After`.
- `ErrBadUpdate` помечает страницу, где часть элементов не разобралась; корректные элементы всё равно возвращаются.

### Хранение курсора
- `loadCursor` / `saveCursor` хранят маркер опроса в файле `gateway_max_cursor` в каталоге состояния Coddy. `saveCursor` пишет во временный файл и переименовывает его, чтобы читатели никогда не видели частичное значение.

## 3. Длинный опрос — `external/gateway/max/poll.go`

`PollLoop` (и тестируемый `pollLoop`) читают поток обновлений до отмены контекста.

- Каждая итерация делает ровно один вызов `Client.fetchUpdates`.
- Обновления передаются в `Handler.Handle` по одному и по порядку; медленный ход не блокирует остальные обновления страницы.
- Курсор сохраняется только после обработки всей страницы. Это даёт семантику **at-least-once**: если процесс остановится посреди страницы, при следующем запуске страница будет переиграна; дедупликация по `message_id` предотвращает повторные ходы.
- Страница с malformed-элементами доставляется и логируется (`ErrBadUpdate`); курсор всё равно продвигается за всю страницу, чтобы цикл не застрял навечно на одном плохом элементе.
- Если `ctx` отменён во время опроса или обработки страницы, цикл завершается корректно.
- Фиксированная пауза (`pollInterval`, по умолчанию 1 с, минимум 1 с, максимум 60 с) делается **после** каждого ответа, но не пока сервер удерживает длинный опрос. Это устраняет вращение со скоростью ~2000 запросов/с, замеченное в эталонном клиенте.

## 4. Диспетчер — `external/gateway/max/dispatch.go`

`Bot.Handle` — это `Handler`, который вызывает цикл опроса.

### Маршрутизация
- `message_callback` → `Bot.HandleCallback` (подтверждает нажатие кнопки и передаёт его ожидающему prompt'у).
- `message_created` → `Bot.handleMessage`.
- Остальные типы обновлений игнорируются.

### Дедупликация и собственные сообщения
- `message_created` дедуплицируются по `MessageID` с помощью ограниченного in-memory набора (`seenIDs`, лимит 4096).
- Обновления с `IsBot == true` отбрасываются: бот не отвечает ни себе, ни другим ботам.

### Проверка доступа
- `allowed` использует `access.EffectiveAccess` и `access.CanAccess` для применения настроенного уровня доступа (`all`, `admins` или `group:<name>`).
- В группах `access.EffectiveIsolation` выбирает режим изоляции; `IsolationAdmin` дополнительно требует, чтобы пользователь был в `cfg.Admins`.

### Ключ сессии
- `sessionstore.SessionKey(adapterName, chatID, userID, isolation, isGroup)` строит стабильный ключ «чат → сессия». Личные чаты всегда используют индивидуальную изоляцию; группы — настроенный режим.

### Очередь воркеров
- `enqueue` держит по одной горутине (`sessionWorker`) на каждый ключ сессии, питаемой каналом ёмкостью `workerQueueCap` = 32. Это гарантирует **один ход на сессию одновременно**.
- Если очередь заполнена, обновление отклоняется с сервисным сообщением.
- Если бот останавливается, обновление не принимается; оно остаётся в потоке для следующего процесса.

### Выполнение хода (`processMessage`)
- Пустой текст → ответ `noTextNote`.
- `/start`, `/help`, `/clear`, `/model`, `/context` обрабатываются локально или делегируются помощникам (см. раздел Команды).
- Для обычных сообщений `ensureSession` получает или создаёт сессию Coddy, `applyInitialModel` ставит последнюю выбранную или первую настроенную модель на свежую сессию, и ход выполняется под `turnContext` (контекст старта без отмены) с таймаутом 10 минут.
- Не-администратор получает `access.NonAdminTurn()` как `session.TurnRestriction` и `sender.refuseApprovals = true`, что ограничивает инструменты и автоматически отклоняет запросы разрешений.
- Отправитель оборачивается в `session.Mirror`, чтобы зеркала ходов видели чат.

## 5. Отправитель — `external/gateway/max/sender.go`

`Sender` реализует `acp.UpdateSender` для одного хода в одном чате.

### Живое сообщение
- Ход порождает одно «живое» сообщение. Оно публикуется при первом значимом обновлении и правится по месту, пока ответ растёт.
- Живой превью показывает последние `previewRunes` = 1500 рун буфера плюс индикатор инструмента (`⚙️ <инструмент>…`), когда инструмент выполняется.
- Правки живого сообщения регулируются не чаще одного раза в `editInterval` = 1 с и ограничены `previewTimeout` = 5 с.

### Финальная доставка (`Flush`)
- `Flush` заменяет живое сообщение окончательным ответом.
- Ответы длиннее `maxTextRunes` = 4000 рун разбиваются на части. Первая часть правит живое сообщение; последующие публикуются как новые сообщения.
- `splitText` предпочитает границы абзацев, строк, затем слов и никогда не режет руну пополам.
- Если контекст хода истёк, доставка всё равно выполняется под `context.WithoutCancel(s.ctx)` с `flushTimeout` = 2 мин.
- Если выполнились только инструменты и буфер пуст, живое сообщение правится на "Done.".

### Документы
- Документ уходит артефактом собственной сессии чата, никогда путём: `session.ToolFile` называет его по id, `toolFilesForSurfaces` (`internal/agent`) публикует его в мете завершённого вызова `share_file`, а отправитель читает ту копию, которую сняла сессия.
- Три обращения: `UploadFile` просит адрес у `POST /uploads?type=file`, отправляет туда байты как multipart в поле `data` без авторизации и читает токен из этого ответа; затем `Send` несёт `{type:file,payload:{token}}`. Оба обращения загрузки идут в темпе записей и не повторяются.
- Тело идёт потоком: `uploadEnvelope` собирает два конца multipart-конверта руками, `io.MultiReader` ставит файл между ними, а запрос сохраняет объявленный `Content-Length`.
- Проверки идут до загрузки: предел размера для этого типа, сам тип, чистка имени, sha256 копии против
  манифеста и `PathInWorkspace` для ограниченного хода. Отказ говорится в чате по-русски.
- На выходе сходятся четыре предела, и решает меньший: 25 МиБ — столько Coddy разрешает захватить
  вызову инструмента как артефакт (100 МиБ на всю сессию, `internal/session/artifacts.go`); 50 МБ —
  наш собственный предел для документа, 250 МБ для видео и 256 МБ для звука
  (`external/gateway/max/documents.go`); платформа принимает документ до 4 ГБ; сам ход длится десять
  минут, а загрузка внутри него — пять. Значит путь документа упирается в 25 МиБ на шаге захвата, а не
  в шлюзе.
- `attachment.not.ready` пережидают, повторяя только сообщение (3/6/9 с, четыре попытки); если сообщение так и не ушло, в журнал пишется `max: upload token unused`, потому что МАКС не даёт удалить копию.
- Одно сообщение несёт один документ; подпись — имя и то, что написал клиент, с обрезкой на `maxTextRunes`.
- Картинка, которую агент **отдал** через `share_file`, едет документом: маршрут фото несёт только то, что модель *читала* (`callImages`), поэтому отбрасывание картинок в `toolFilesForSurfaces` теряло их молча — веб показывал карточку, а чат не получал ничего.

### Клавиатуры и prompt'ы
- Запросы разрешений и вопросы с вариантами ответа рисуются как inline-клавиатуры (`attachments` в `client.go`).
- `Button.Payload` имеет вид `ask:<token>:<index>`; нажатие возвращается как обновление `message_callback`.
- `askOptions` публикует prompt, ждёт из канала и «закрывает» сообщение (убирает клавиатуру, добавляет примечание) при ответе или по завершении хода.
- `Bot.HandleCallback` / `resolvePress` подтверждают нажатие через `AnswerCallback` и передают выбор ожидающему prompt'у. Устаревшие или чужие нажатия подтверждаются, но игнорируются.

### Обработка не-админов
- Когда установлен `refuseApprovals`, каждый запрос разрешения возвращает `cancelled`/`reject` без показа клавиатуры.

## 6. Команды — `external/gateway/max/commands.go`

`parseCommand` разбивает `/word rest` на команду и аргументы. `knownCommand` распознаёт команды адаптера и settings-команды; неизвестные слэш-команды игнорируются.

- `/start` — приветствие.
- `/help` — список команд из `helpText()`.
- `/clear` — сбрасывает ключ сессии (`store.Reset`), забывает старую живую сессию, отвечает «Начата новая беседа.»
- `/model` без аргументов — сообщает текущую эффективную модель и список настроенных моделей.
- `/model <id>` — при точном вводе `session.ParseSettingsCommands` разбирает его, и шлюз запоминает модель в `store.SetLastModel` (только админам), чтобы свежие сессии начинались с неё.
- `/context` — выводит разбор контекста сессии через `formatContextBreakdown`.
- Settings-команды (`/agent`, `/plan`, `/ask` и др.) пропускаются в сессию; `changesSettings` их определяет. В группах settings-команды разрешены только админам (`adminOnlyNote`).

## 7. Модели провода — `external/gateway/max/model.go`

Типы отражают payload MAX Bot API:

- `Update` — событие верхнего уровня с `UpdateType`, `Timestamp`, `ChatID`, `UserID`, `MessageID`, `User` и сырыми телами `Message` / `Callback` (`json.RawMessage`).
- `Message` — `Sender`, `Recipient`, `Timestamp`, `Body`.
- `Text` — `Mid`, `Seq`, `Text`.
- `Recipient` — `UserID`, `ChatID`, `ChatType`.
- `Callback` — `CallbackID`, `Payload`, `Timestamp`, `User`.
- `User` — `UserID`, `FirstName`, `LastName`, `Username`, `Name`, `IsBot`; `DisplayName()` строит читаемое имя.
- `Target` — `UserID` или `ChatID`; в исходящем сообщении задан ровно один из них.
- `Button` — `Type`, `Text`, `Payload`.
- `Outgoing` — `Target`, `Text`, `Format`, `Buttons`.

Тела хранятся как `json.RawMessage`, чтобы malformed внутренний объект не ломал разбор всей страницы; адаптер разбирает только нужные поля.

## 8. Проводка и конфигурация

### Проводка шлюза
- `external/gateway/serve_max.go` (тег сборки `gateway || gateway.max`) создаёт `Bot` и запускает его через `gateway.Hub`. Файлы `gateway_max_sessions.json` и `gateway_max_cursor` хранятся в `cfg.ResolvedSessionsRoot()` — каталоге состояния Coddy, а не рабочем каталоге процесса.
- `external/gateway/serve_max_stub.go` (тег сборки `!(gateway || gateway.max)`) устанавливает `MaxAvailable = false` и возвращает ошибку при вызове.
- `cmd/coddy/serve.go` регистрирует подсистему МАКС (`KindGatewayMax`, тег сборки `gateway`, отпечаток `gateway.MaxFingerprint`). Флаг `--gateway` управляет Telegram; МАКС следует за `gateways.max.enable`.

### Конфигурация
- `internal/config/gateway.go` определяет `MaxGatewayConfig` с полями: `Enabled`, `Token`, `Proxy`, `CAFile`, `PollTimeoutSeconds`, `PollIntervalSeconds`, `Admins`, `DefaultAccess`, `DefaultIsolation`, `UserGroups`, `Chats`.
- Значения по умолчанию: таймаут опроса 30 с, интервал опроса 1 с, доступ `all`, изоляция `individual`.
- Разрешение токена: `EffectiveToken()` возвращает настроенный токен или переменную окружения `MAX_BOT_TOKEN`.
- Валидация проверяет формат прокси, наличие файла CA и диапазон опроса.
- `internal/config/config.schema.json` документирует те же ключи внутри `gateways.max`.

### Теги сборки
- Файлы адаптера: `//go:build gateway || gateway.max`.
- Заглушка: `//go:build !(gateway || gateway.max)`.
- Сборка с `-tags gateway` или `-tags gateway.max` включает адаптер.

## Допущения и примечания

- Документ считает `gateway_max_sessions.json` и `gateway_max_cursor` стабильными именами файлов; они заданы литералами в `serve_max.go`.
- Точный набор инструментов не-админа определён в `external/gateway/access/turn.go`; адаптер потребляет его через `access.NonAdminTurn()`, не перечисляя список сам.
- Разделение ответственности между `poll.go` (курсор после страницы) и `client.go` (`fetchUpdates` не двигает курсор) обеспечивает гарантию at-least-once; `Updates()` задокументирована, но цикл использует `fetchUpdates`.
- Обновление `message_callback` несёт id сообщения, которому принадлежит кнопка, в `message.body.mid`, а своего `message_id` не имеет. `Update.MessageKey` читает тот id, что пришёл; меню модели правится именно по нему, а чтение собственного поля обновления дало бы пустой id и отказ API.
